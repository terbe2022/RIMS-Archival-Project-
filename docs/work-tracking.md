# Work tracking

GitHub Issues and the actual GitHub Project hold actionable work. Repository documents explain architecture, decisions, current capability and handoffs. Do not create a competing Markdown task system.

Read actual Project fields when an authorized Project tool is available. An open issue does not prove a board status, owner, priority or deadline. Match updates by scope and acceptance criteria, retrieve the existing issue first, and flag uncertain matches rather than forcing a relationship.

Tayler handles engineering and integration; Gauri handles validation. Use the appropriate contributor branch and pull request for reviewed changes. Reported progress, proposed changes, inspected code, test results and server verification are distinct evidence levels. Close work only with its acceptance evidence.

Teams updates produce traceable proposals. The exact proposed GitHub change requires human approval and authorized executor validation before submission. See [Teams coordination](TEAMS-PROGRAM-MANAGER.md), the [program-manager role](PROGRAM-MANAGER.md), and [historical conventions](history/docs/work-tracking.md).
