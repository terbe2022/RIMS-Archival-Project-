# RIMS archival triage — status

4 September 2026. Written to be read without the build conversation.

---

## Where this stands in one paragraph

A working pipeline runs end to end on real accession material, on CPU, in under
ten seconds per thousand files. It reads an archivist's intake form, crawls an
accession, identifies formats by content signature, removes duplicates and
system noise, applies the appraisal rules, sorts every file into a processing
lane, extracts text from documents and spreadsheets, ranks everything against
the collection's own stated priorities, and writes one manifest row per file
with the reason for every decision attached. A review interface reads that
manifest and lets an archivist confirm or override each call, recording who
decided and whether they agreed with the machine.

What it does not yet do is read email or describe images. Those were the two
strongest POCs and neither is ported. Until they are, this is a triage and
routing system, not a description system.

## Proven on real material

ACC-2026-022, the Hart correspondence sample, 901 files:

| | |
|---|---:|
| Files processed | 901 |
| Time, CPU only | 9.7 s |
| Text extracted | 1,118,598 characters from 50 files |
| Selected by rule | 798 |
| No rule had an opinion | 101 |
| Routed to a supervising archivist | 2 |
| Discarded | 0 |

**The most useful result was not a number.** The intake form says this folder is
"really three or four things that have been put in one folder" and describes
four provenances. Routing found them from file signatures alone:

- 800 email — the Hart correspondence itself
- 46 documents — against the form's forty-four 1994 administrative PDFs
- 6 spreadsheets and databases — the Ethiopian fieldwork collection
- 32 images, 1 video, and exactly 15 unroutable `.mht` web captures — the form
  counts fifteen saved web pages

An archivist arrived at that description by reading the folder. The pipeline
arrived at the same partition in under ten seconds, and flagged two lanes the
form had not declared. That is the case for splitting the accession, made from
evidence rather than assertion.

## The exclusion percentage: what we can and cannot say

Measured: **0.0% of 901 files** fell into layer 0.

This is correct and it is not a result about the architecture. The sample is the
*output* of an exclusion pass — the sampling script already removed the
duplicates and system files that define the measurement. Running an exclusion
pass over it finds nothing left to exclude.

The sampler's own record is real evidence on real material:

| | |
|---|---:|
| Loose files considered | 672 |
| Excluded before the sample existed | **573 (85.3%)** |
| of which duplicates | 561 (83.5%) |

That is higher than the 40–70% working estimate, but it is not the same
measurement and the difference must be stated. The real figure needs the
pipeline pointed at material upstream of the sampler.

## What is not built

**Email.** 800 files routed, none read. POC 1's own README lists defects that
must be fixed before it touches a real accession — most seriously, PII
placeholder numbering restarts per document, so `<PERSON1>` means a different
person in every message. Masked output produced that way looks correct and is
not. Thread decomposition, header parsing and summarisation are all unported.

**Images.** 32 files routed, none described. Needs a vision model. POC 3's
73% ambiguous flag rate was a specification problem rather than a model one, so
a labelled gold set is a prerequisite rather than a follow-up.

**Semantic search.** POC 2's extraction is replaced and now runs on Linux
without Microsoft Office, which the original could not. Its search index is not
rebuilt.

**Databases and video.** No extractor for `.mdb` or `.mov`. Both were on POC 2's
never-implemented list.

## Blocked on people, not on code

**One number unblocks the most valuable run.** ACC-2026-021, the Hanratty office
computer, needs a record series number from an accessioning archivist. Nothing
else about it is missing. It is the accession that exercises most of what was
built: thirty-eight files that lost their extensions, Dropbox conflict copies,
and the drafts rule.

**The appraisal rules have never been confirmed.** They are version
`0.1-draft`, written from answers given in August, and they encode two
deliberate departures from what was said — personal finance and HR material are
routed to a supervising archivist rather than set aside, because discarding
unread records is not recoverable. Both should be confirmed or overruled
explicitly. There is now a live case attached: two files matched the personal
finance rule, both on the word "mortgage" in a filename, one of them in public
mailing list traffic.

**ACC-2026-020 stays draft.** Nobody has said what the images depict. The
pipeline characterises them and refuses to appraise them, which is the correct
behaviour and worth demonstrating.

## Two things worth doing tonight, neither blocked

**Install Siegfried.** 802 of 901 files were typed by extension rather than
content, because no format identification tool is installed. It is a single Go
binary needing no administrator access. It matters most for ACC-2026-021, where
extensionless files are the whole point.

**Pin pandas and pyarrow together.** A crash appears on some parquet access
paths — the query succeeds, prints, then aborts at interpreter shutdown. The
data is fine, but it will resurface when the review interface reads the same
file.

## The GPU is no longer the constraint

The legislation pipeline was reserving 90% of the card by configuration rather
than need. That has been capped, leaving roughly 15 GB free continuously from
the next restart. Confirm the pre-cap instance has exited before relying on it.

This changes the order of work. Email and image processing were deferred because
the card was unavailable. It is now available, and those are the two largest
remaining gaps.

## Recommended order

1. Get the record series for ACC-2026-021 and run it.
2. Install Siegfried; re-run both accessions.
3. Confirm or overrule the appraisal rules, using the live personal-finance case
   as the concrete question.
4. Port the email lane, with POC 1's placeholder-stability defect fixed first.
5. Port the image lane, after a labelled sample exists to score against.

Steps 1–3 need no GPU and no further building. Steps 4 and 5 are where the
remaining engineering is.

## On publishing

Code can go in the public repository. Data cannot, including redacted data —
measured redaction recall is 0.69–0.81 and a summary of an email is still about
a real person. A public demonstration build exists that replaces every filename
with a placeholder, carries no file content, and refuses to write if anything
identifying survives. That is what a public page should serve.
